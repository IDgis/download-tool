# Stage 3: Play 2.6 → 2.7 → 2.8 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Rewritten after Stage 2 execution (2026-08-05).** The original version of this plan assumed `controllers.WebJarAssets` still existed going into Play 2.7/2.8, and that `play.Play.application()`/`play.Configuration` only needed replacing at 2.8. Both assumptions were wrong, verified against the actual published jars — see the corrections below.

**Goal:** Advance Play from 2.6 to 2.8. The two things that actually force code changes in this range are: (1) `play.Play` and `play.Configuration` — the Java-facing wrapper classes, not just individual deprecated methods — are removed **entirely at Play 2.7.0**, one version earlier than originally planned; every constructor that takes `play.Configuration`, plus `layout.scala.html`'s `play.Play.application()` calls, must migrate to `com.typesafe.config.Config` in micro-commit 1. (2) The `response()` mutation API is removed piecemeal: `response().setHeader()` is removed at Play 2.8 as originally planned (micro-commit 2), but `response().setContentType()` turned out to already be gone at 2.7.9 — one version earlier than assumed — see the correction on micro-commit 1 Task 2 Step 6.

**Corrected during Stage 3 execution (2026-08-07), beyond the two points above** — found while actually running the migration, not caught by the pre-execution `javap` pass: (a) `ZooKeeper.java`/`DownloadModule.java` turned out to be fully dead code since a 2016 commit (never wired into Guice, no config anywhere) — deleted rather than ported; see the correction on micro-commit 1 Task 2 Step 7; (b) `ErrorHandler.java` only had `config` as a constructor parameter, not a field — see the correction on micro-commit 1 Task 2 Step 8; (c) `play.test.Helpers.route(...)` changed signature at `play-test_2.12:2.7.9`, breaking `web/test/SmokeTest.java` (outside this plan's original file scope) — see the correction on micro-commit 1 Task 2 Step 11; (d) micro-commit 2 turned out to be far from "just `response()` removal in two controllers" — `Controller.request()` (no-arg) is also removed entirely at 2.8, along with the deprecated `implicitJavaMessages` conversion that silently supplied `Messages(...)` calls, and `JavaScriptReverseRouter.create()`'s short overloads (which had themselves silently depended on `Http.Context` for their `host` default) — all three forced changes to `DownloadForm.java`, `form.scala.html`, and `web/conf/routes`, none of which are `response()`-related and none of which were in this plan's original file list. See the correction on micro-commit 2 Task 3 Step 4. All three went undiscovered for a while because this project's mixed Scala/Java compilation only reaches `javac` (and therefore any pure-Java compile error) after the Scala-side Twirl compilation succeeds — worth remembering for later stages too.

**Not in this stage's scope:** the `WebJarAssets` → `WebJarsUtil` migration. It was originally planned for this stage but turned out to be forced at Play 2.6 itself (the `webjars-play_2.12` artifact dropped `controllers.WebJarAssets` starting at its very first `_2.12` release), so it was already completed during Stage 2. If you're looking at this plan and `WebJarAssets` references still exist in the codebase, something is out of sync — check Stage 2's plan/status first.

**Architecture:** Two micro-commits on one branch, same as originally planned. Micro-commit 1 (Play 2.7) is the large, mostly-mechanical change (every `play.Configuration` usage across the app, plus the `layout.scala.html` config-threading). Micro-commit 2 (Play 2.8) starts from `response()` removal in two controllers, as originally planned, but — per the correction above — turned out to also require threading `Http.Request` into `DownloadForm.java`'s `get`/`post`/`jsRoutes` (plus matching `web/conf/routes` changes) and injecting `MessagesApi` for `form.scala.html`, since three more APIs silently depended on the same removed `Http.Context` thread-local. Not the "comparatively small" change this plan originally described.

**Tech Stack:** Gradle 8.8, Play 2.7.9 (intermediate) → 2.8.22, Scala 2.12, Java 8

**Verified facts this plan relies on** (checked via `javap` against the actual published jars, not assumed):
- `play/Play.class` and `play/Configuration.class` (top-level `play` package) exist in `play_2.12:2.6.25`, are both **absent** from `play_2.12:2.7.9` and `play_2.12:2.8.22`. Only `play.api.Play`/`play.api.Configuration` (Scala side) remain.
- `com.typesafe.config.Config` has **no default-value overloads** (`getString(path)` throws `ConfigException.Missing` if absent; there is no `getString(path, default)`). Use `hasPath(path)` to guard optional keys.
- `Controller.response()` (and `ctx()`, `session()`, `flash()`, `lang()`, and — confirmed during Stage 3 execution, not in the original plan — `request()`) exist in `play_2.12:2.7.9`, are **absent** from `play_2.12:2.8.22` (only `TODO(Http.Request)` and the static `Results` helpers remain on `Controller`/`Results`). `request()`'s removal was confirmed two ways: `javap -p` shows no such method anywhere in the `Controller`/`Results` hierarchy at 2.8.22, and an isolated `javac` compile of a minimal subclass against the real 2.8.22 jars fails with `cannot find symbol`.
- `org.webjars:webjars-play_2.12` continues under the `org.webjars` Maven group through at least `2.8.18` — it does **not** rename to `org.webjars.play` (that's the Java package name inside the jar, not the Maven groupId; confirmed no artifacts exist under the `org.webjars.play` group).
- `play.core.j.PlayMagicForJava.implicitJavaMessages` (deprecated since 2.7.0, flagged by a compiler warning during micro-commit 1 — that warning was the advance notice) is **removed** at `play_2.12:2.8.22` — confirmed via `javap`. Any template calling `Messages(...)` without an explicit `MessagesProvider` in scope needs one threaded in manually now.
- `play.routing.JavaScriptReverseRouter.create(...)` has three overloads at `play_2.12:2.7.9` (1/2/3 leading `String` args before the `JavaScriptReverseRoute...` varargs) but only the full 3-`String`-arg form at `play_2.12:2.8.22` — confirmed via `javap`. The removed short overloads (checked against the `2.7.9` sources jar) delegated their omitted `host` argument to `Http.Context.current().request().host()` — another silent `Http.Context` dependency, same root cause as `request()`'s removal.
- **Build gotcha, not a Play API fact:** `:web:compilePlayTwirlTemplates` does not reliably invalidate on a bare `playVersion` bump — verify each micro-commit with `./gradlew clean build` (at least once), not plain `build`, or you may compile against stale pre-bump generated Twirl output and see misleading errors.
- **Build gotcha #2:** this project's mixed Scala/Java compilation (`:web:compileScala`) only invokes `javac` on the `.java` sources *after* the Scala-side (Twirl-generated) sources compile successfully. A Scala-side failure means Java-side errors — including in files with zero Scala-related changes — stay completely invisible until the Scala side is fixed and the build is run again.
- `play-ahc-ws_2.12` and `play-guice_2.12` both track normal Play versioning through `2.7.9`/`2.8.22` — no further renames at this stage.

- [ ] **Step 2: Migrate `util/Cache.java`**

Only call site is `config.getString("cache.path")` with no default — `application.conf` sets `cache.path = ${ZIP_CACHEPATH}` as a required substitution, so this key is always present by the time the app boots (an unresolved required substitution fails application startup, not this call). Straight type swap:

```java
import java.nio.file.FileSystems;
import java.nio.file.Files;
import java.nio.file.Path;

import com.typesafe.config.Config;

import controllers.DownloadResult;

import play.Logger;
import play.Logger.ALogger;

public class Cache {

	private static final ALogger log = Logger.of(Cache.class);

	static public Path get(Config config) {
		String cachePath = config.getString("cache.path");

		log.debug("cache.path: " + cachePath);

		Path cache = FileSystems.getDefault().getPath(cachePath);

		if(!Files.exists(cache)) {
			throw new IllegalArgumentException("configured cache location doesn't exists");
		};

		return cache;
	}
}
```

Note: the old `if(cachePath == null)` guard is removed — `Config.getString` throws instead of returning `null`, so that branch was already unreachable in practice (the key is guaranteed present or the app fails to boot) and is now provably unreachable.

- [ ] **Step 3: Migrate `data/MetadataProvider.java`**

Change the import and constructor parameter from `play.Configuration` to `com.typesafe.config.Config`. Every call site except one is a required substitution in `application.conf` (`metadata.url`, `metadata.confidential-path`, `download.trusted.header`, `download.access` are all non-optional `${VAR}` substitutions) and is a direct swap. **The one exception:** `metadata.data-public-value` is declared as `data-public-value=${?DATA_PUBLIC_VALUE}` (optional substitution) in `application.conf`, and `MetadataProvider.get()` explicitly checks `if(dataPublicValue == null ...)`. `Config.getString` would throw instead of returning null here — this must be guarded with `hasPath`:

```java
import java.net.URL;
import java.net.MalformedURLException;
import java.util.Optional;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.CompletionStage;

import javax.inject.Inject;

import models.MetadataDocument;

import com.typesafe.config.Config;

import play.libs.ws.WSClient;

public class MetadataProvider {

	private final Config config;

	private final WSClient ws;

	@Inject
	public MetadataProvider(Config config, WSClient ws) {
		this.config = config;
		this.ws = ws;
	}

	public String getTrustedHeader() {
		return config.getString("download.trusted.header");
	}

	public String getTrustedValue() {
		String access = config.getString("download.access");
		if("intern".equals(access)) {
			return "1";
		} else {
			return "0";
		}
	}

	public CompletionStage<Optional<MetadataDocument>> get(String id) {
		try {
			URL url = new URL(config.getString("metadata.url") + id + ".xml");
			return ws.url(url.toExternalForm())
				.setFollowRedirects(true)
				.setHeader(getTrustedHeader(), getTrustedValue())
				.get()
				.thenApply(response -> {
					if(response.getStatus() == 200) {
						MetadataDocument metadataDocument = new MetadataDocument(url, response.asXml());

						String confidentialPath = config.getString("metadata.confidential-path");
						String dataPublicValue = config.hasPath("metadata.data-public-value")
							? config.getString("metadata.data-public-value")
							: null;
						if(dataPublicValue == null
							|| metadataDocument.getresourceConstraints(confidentialPath)
								.contains(dataPublicValue)
							|| "intern".equals(config.getString("download.access"))) {
							return Optional.of(metadataDocument);
						}
					}

					return Optional.<MetadataDocument>empty();
				});
		} catch(MalformedURLException e) {
			CompletableFuture<Optional<MetadataDocument>> failed = new CompletableFuture<>();
			failed.completeExceptionally(e);
			return failed;
		}
	}
}
```

<summary>Superseded: the abandoned line-by-line port, and the two corrections made to it before the dead-code discovery (kept for history only — do not implement)</summary>

The original plan called for a full `Configuration` → `Config` replacement of `ZooKeeper.java`, using `Configuration`'s default-value overloads extensively (`getString(path, default)`, `getStringList(path, default)`, `getBoolean(path, default)`, `getInt(path, default)`) and `.getConfig(path)`/`.keys()` for nested iteration, none of which exist the same way on `com.typesafe.config.Config`.

Two corrections were made to that port before the dead-code discovery superseded it entirely:

1. **The two `getConfig(...)` calls must not be `hasPath`-guarded.** The plan originally assumed `Configuration.getConfig()` returned an empty `Configuration` when the path was absent, and guarded the two blocks reading `service.domain.additionalConfig`/`service.securedPaths` with `hasPath` to skip them silently. Checking the actual `play_2.12:2.6.25` source (`play/Configuration.java`) showed this was wrong — it returns `null`, not an empty `Configuration`:
   ```java
   public Configuration getConfig(String key) {
     scala.Option<play.api.Configuration> nConf = conf.getConfig(key);
     if (nConf.isDefined()) {
       return new Configuration(nConf.get());
     }
     return null;   // not an empty Configuration — null
   }
   ```
   The original code called `.keys()` on that result with no null check, so the pre-Stage-3 app already crashed via `NullPointerException` on a deployment missing either section — these were never soft/optional, and `hasPath`-guarding them would have been a silent-skip regression, not a faithful port.

2. **`.keys()` needs an `entrySet()`-based replacement, not `.root().keySet()`.** Checked `play.api.Configuration.scala`: `keys` and `subKeys` are different operations —
   ```scala
   def keys: Set[String] = underlying.entrySet.asScala.map(_.getKey).toSet          // recursive, full leaf paths
   def subKeys: Set[String] = underlying.root().keySet().asScala.toSet              // direct children only
   ```
   `Config.root().keySet()` is the equivalent of `Configuration.subKeys()`, not `Configuration.keys()`. They only coincide when a config section has no nesting deeper than one level, which couldn't be confirmed from this repo — `service.domain.additionalConfig`/`service.securedPaths` aren't defined in `web/conf/application.conf` at all (that's what prompted the dead-code investigation in the first place). The faithful replacement would have been a small `entrySet()`-based `keys(Config)` helper.

Neither correction ended up mattering once the dead-code finding landed — see Step 7 above.

**Use `clean build`, not plain `build`, the first time you verify this micro-commit.** Discovered during Stage 3 execution: `:web:compilePlayTwirlTemplates` doesn't reliably invalidate its cache on a bare `playVersion` bump — a plain `./gradlew build` right after changing `playVersion` in Step 1 can silently recompile against **stale, pre-bump generated Twirl output**, producing confusing errors (e.g. `value Context is not a member of object play.mvc.Http` from templates that were generated under the *old* Play version's default imports, not the new one). `./gradlew clean build` forces regeneration and avoids this entirely. Once you've done one clean build successfully, ordinary `./gradlew build` is fine again.

**Corrected during Stage 3 execution (2026-08-07): three more APIs break at Play 2.8, none of them `response()`-related, none caught until a clean build actually let `javac` run.** Root cause of why these went undiscovered for a while: this project's mixed Scala/Java compilation runs as a single `:web:compileScala` task — Zinc compiles the Twirl-generated `.scala` files first, and only proceeds to `javac`-compile the `.java` files (including every controller) if that first phase succeeds. Until the Twirl/Scala-side errors above were fixed, `javac` never got a chance to even look at `DownloadForm.java`, so its errors stayed completely invisible. **After fixing the Scala-side issues, re-run the build again — don't assume `BUILD SUCCESSFUL` on the first green Scala compile; the Java phase may not have run yet.**

1. **`Messages(...)` calls need an explicit `MessagesProvider` now.** `form.scala.html`'s `@Messages(error.message)` previously worked via a deprecated implicit conversion (`play.core.j.PlayMagicForJava.implicitJavaMessages`, flagged as deprecated-since-2.7.0 in the compiler warning during micro-commit 1 — that warning was the advance notice) that derived `Messages` from the thread-local `Http.Context`.    private final MessagesApi messagesApi;
