# Stage 6: Java 11 → 17 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade the Java runtime target from 11 to 17, with specific attention to `nl.idgis.commons:commons-cache:0.0.15` which may use internal JDK APIs that Java 17's strong-encapsulation boundary blocks, and to `org.easymock:easymock:3.4` (see correction below — confirmed broken, not just "may" be).

**Architecture:** The same three-place update as Stage 4 (build platform, Dockerfiles, CI). The additional risk is `commons-cache:0.0.15`, a private IDgis library used in the `downloader` module that may call internal JDK APIs. The `Security Manager` was removed in Java 17 but that doesn't affect this codebase. Spring JDBC 5.3.39 and PostgreSQL driver 42.7.7 are both clean on Java 17.

> **Additional risk found during Stage 4 execution (2026-08-12), not in this plan's original scope: `org.easymock:easymock:3.4` (pinned directly in the root `build.gradle`'s `testImplementation`, unrelated to Play/Guice) is confirmed broken on Java 17, not just at risk.** The Stage 4 Java 11 build already printed an illegal-reflective-access *warning* from `org.easymock.cglib` touching `ClassLoader.defineClass` reflectively. Checked EasyMock's own release history: EasyMock 4.x is reported to throw a hard `InaccessibleObjectException` on Java 17 (cglib genuinely cannot work around JPMS there), and EasyMock only fixed this by replacing `cglib` with ByteBuddy in **5.0.0**. This is completely independent of the Play version bump (easymock isn't a Play dependency at all) — see the new Task 6 below, needed in addition to Task 5's `commons-cache` check.

**Tech Stack:** Gradle 8.8, Play 2.9.x, Java 17, Zulu JDK 17

### Before you start

- Prerequisite: Stage 5 complete (`./gradlew build` passing on `develop`) — **Stage 5 is currently BLOCKED** (found 2026-08-12): `org.gradle.playframework` has no version supporting Play 2.9. See the banner at the top of Stage 5's plan before assuming this prerequisite is met.
- Branch: `migration/stage-6-java-17` (cut from `develop` — this repo follows git-flow; `develop` is the integration branch, `master` is release-only)
- Verify command: `./gradlew build`
- **Every `./gradlew build` in this stage must be run with `JAVA_HOME` explicitly pointed at a JDK 17** (found during Stage 4 execution, 2026-08-12): the `org.gradle.playframework` plugin's `javaVersion` setting is not self-enforcing — no toolchain is configured in this project, so whichever JDK `JAVA_HOME` points to silently compiles at its own native bytecode level, no error or warning either way, even if it's lower than the declared `javaVersion`. Confirmed empirically at Stage 4 (Java 11): identical `build.gradle`, `BUILD SUCCESSFUL` both times, but class-file major version differed (55 vs 52) purely based on which JDK ran the build. A green build under a stale `JAVA_HOME` here would look identical to a real Java 17 build and prove nothing. Optionally spot-check: `javap -v web/build/classes/scala/main/controllers/DownloadForm.class | grep "major version"` should read `61` (Java 17) after a real verification build.

### Task 5: Verify `commons-cache:0.0.15` at Java 17

**Files:** none

- [ ] **Step 1: Build the downloader module in isolation**

```bash
./gradlew :downloader:build
```

Watch specifically for `InaccessibleObjectException` or `module ... does not open ... to unnamed module` errors. These indicate that `commons-cache:0.0.15` is calling internal JDK APIs blocked by Java 17 strong encapsulation.

- [ ] **Step 2: If no encapsulation errors appear**

Proceed to full build verification.

- [ ] **Step 3: If encapsulation errors appear**

Options, in order of preference:
1. Upgrade `commons-cache` to a newer version that does not use internal APIs.
2. Add `--add-opens` JVM flags to the `downloader` run task in `build.gradle`:
   ```groovy
   project(':downloader') {
       run {
           jvmArgs '--add-opens', 'java.base/java.lang=ALL-UNNAMED'
           // add the specific module/package reported in the error
       }
   }
   ```
   This is a workaround — prefer a library update.

- [ ] **Step 4: Run the full build**

```bash
./gradlew build
```

Expected on the first attempt: **fails** at `:queue:test` (or wherever `easymock` mocks are used) with `InaccessibleObjectException` from `org.easymock.cglib` — see Task 6 below, added during Stage 4 execution, not in this plan's original scope.

### Task 6: Bump `easymock` to fix a Java 17-breaking `cglib` dependency

**Files:**
- Modify: `build.gradle` (the root `testImplementation 'org.easymock:easymock:3.4'` line)

**Added during Stage 4 execution (2026-08-12).** `easymock:3.4`'s bundled `cglib` reflectively calls `ClassLoader.defineClass` — this only warns on Java 11 (seen in Stage 4's build output) but throws `InaccessibleObjectException` on Java 17, where illegal reflective access is denied by default. This is a project-owned test dependency, not pulled in by Play, so no Play version bump fixes it.

- [ ] **Step 1: Bump the version**

```groovy
testImplementation 'org.easymock:easymock:5.4.0'   // verify latest 5.x on Maven Central before using
```

EasyMock replaced `cglib` with ByteBuddy starting at 5.0.0 specifically to fix this class of JPMS/Java 17 issue.

- [ ] **Step 2: Check for API breaks**

EasyMock 4.0/5.0 each had some API changes (e.g. `mock()` overload resolution, `replay`/`verify` behavior around strict mocking). Run `./gradlew :queue:test` (or wherever `easymock` is used — check via `grep -rl easymock` in test sources) after the bump and fix any compile/test breaks before moving on.

- [ ] **Step 3: Run the full build again**

```bash
./gradlew build
```

Expected: `BUILD SUCCESSFUL`, no illegal-reflective-access warnings or `InaccessibleObjectException` from `easymock`/`cglib` anywhere in the output.
