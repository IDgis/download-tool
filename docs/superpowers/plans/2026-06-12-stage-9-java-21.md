# Stage 9: Java 17 → 21 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade the Java runtime target from 17 to 21. No Play or application code changes.

**Architecture:** The same three-place update as Stages 4 and 6: Gradle play platform, Docker base images, CI workflow. Java 21 brings virtual threads as an optional enhancement but the codebase does not need to use them. The Security Manager was fully removed in Java 17 so there are no additional breaking changes at Java 21 for this codebase.

**Tech Stack:** Gradle 9.x, Play 3.0.x, Java 21, Zulu JDK 21

---

### Before you start

- Prerequisite: Stage 8 complete (`./gradlew build` passing on `develop`) — **as of 2026-08-12, Stages 5 through 8 are all blocked** behind `org.gradle.playframework` having no Play 2.9 support (see the banner at the top of `docs/superpowers/plans/2026-06-12-stage-5-play-29.md`). Don't assume this prerequisite is reachable without checking that blocker's status first.
- Branch: `migration/stage-9-java-21` (cut from `develop` — this repo follows git-flow; `develop` is the integration branch, `master` is release-only)
- Verify command: `./gradlew build`
- **Every `./gradlew build` in this stage must be run with `JAVA_HOME` explicitly pointed at a JDK 21** (found during Stage 4 execution, 2026-08-12; re-verify this is still true if Stage 7's Gradle 9 bump changed anything about toolchain handling): the `org.gradle.playframework` plugin's `javaVersion` setting is not self-enforcing on Gradle 8 — no toolchain is configured in this project, so whichever JDK `JAVA_HOME` points to silently compiles at its own native bytecode level, no error or warning either way, even if it's lower than the declared `javaVersion`. Confirmed empirically at Stage 4 (Java 11): identical `build.gradle`, `BUILD SUCCESSFUL` both times, but class-file major version differed (55 vs 52) purely based on which JDK ran the build. A green build under a stale `JAVA_HOME` here would look identical to a real Java 21 build and prove nothing. Optionally spot-check: `javap -v web/build/classes/scala/main/controllers/DownloadForm.class | grep "major version"` should read `65` (Java 21) after a real verification build — file path may differ if `DownloadForm.java` moved by this stage.
